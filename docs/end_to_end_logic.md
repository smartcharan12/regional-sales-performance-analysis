# How Everything Connects: the End-to-End Logic

This document explains **why each stage of the project exists, and how each one feeds the next**. It assumes no knowledge of data analytics.

To make it concrete, we follow **one real row of the data** through every stage:

> **Order US-2024-100748**: a Corporate customer in **Houston, Texas** bought **10 Heavy-Duty Shredders** on 26 March 2024, at a **40% discount**.

(Technical file-and-module view: [architecture.md](architecture.md). Beginner vocabulary: [START_HERE.md](../START_HERE.md).)

---

## The chain at a glance

```
RAW DATA ─► UNDERSTANDING ─► QUALITY CHECK ─► CLEANING ─► FEATURE ENGINEERING ─► EDA
   ─► BUSINESS QUESTIONS ─► SQL ANALYSIS ─► STAR SCHEMA ─► DAX ─► POWER BI
   ─► INSIGHTS ─► RECOMMENDATIONS
```

| Stage | In one sentence |
|---|---|
| Raw data | What the sales system recorded, including its mistakes |
| Understanding | Learn what a row and each column mean |
| Quality check | List exactly what is wrong |
| Cleaning | Fix what can be fixed, remove only what can't be trusted |
| Feature engineering | Add columns that make questions easy (year, margin, discount amount) |
| EDA | Look at the data from every angle to find patterns |
| Business questions | Turn patterns into precise answers for managers |
| SQL analysis | Ask the same questions of a database, as an independent check |
| Star schema | Organise the data the way BI tools work best |
| DAX | Formulas that recalculate for whatever a manager selects |
| Power BI | The interactive report managers actually use |
| Insights | What the numbers mean, separated from what we guess |
| Recommendations | What to do, who should do it, and how to check it worked |

## 1 · Raw data

**What enters:** nothing. This is the starting point: `data/raw/sales_raw.csv`, 11,567 rows (generated by `src/generate_data.py`; the data is synthetic).
**What it looks like:** our example row, exactly as exported:

```
US-2024-100748, 2024-03-26, 2024-03-31, Standard Class, RB-10481, Ravi Brown D., Corporate,
United States, Houston, Texas, <blank>, OFF-AP-1005, Office Supplies, Appliances,
Heavy-Duty Shredder G863, 207.3, 10, 0.4, -39.18
```

Notice the **blank Region** (between "Texas" and "OFF-AP-1005"). Thousands of other rows have problems too: duplicates, `"$1,277.10"` stored as text, `east` vs `East`, impossible dates.

**Why this stage exists:** analysis is only as good as its input, so we have to start from what the business really records, mess included.
**What comes out:** a file we don't trust yet.
**How the next stage uses it:** it reads the file to learn its structure.

## 2 · Data understanding → `notebooks/01_data_understanding.ipynb`

**What enters:** the raw file.
**What happens:** we look *before* changing anything. How many rows and columns? What does one row mean? What type is each column?
**Key discovery:** one row is one **product on one order** (an *order line*). Order US-2024-100748 could contain several products, so the same Order ID repeating is **normal**, not a duplicate.
**What comes out:** the meaning of every column ([data dictionary](data_dictionary.md)) and the "grain" of the data.
**Why it exists:** you can't recognise "wrong" until you know what "right" looks like. If we'd treated repeated Order IDs as duplicates, we would have deleted real sales.
**How the next stage uses it:** the quality check knows which values are acceptable (e.g. Region must be one of four, Discount between 0 and 0.8).

## 3 · Data quality check → notebook 01 (Part 7) + `sql/data_quality.sql`

**What enters:** the raw data plus the rules from stage 2.
**What happens:** we count every type of problem. For our row: **Region is missing**. Across the file: 35 missing regions, 70 duplicate rows, 30 sales stored as text, 18 discounts typed as "20" instead of "0.2", 5 impossible order dates, and so on.
**What comes out:** an issue list, with a planned treatment and a reason for each issue.
**Why it exists:** cleaning without a list is guesswork. The list also lets someone else review our decisions.
**How the next stage uses it:** the issue list *is* the cleaning plan.

## 4 · Data cleaning → `src/data_cleaning.py`, notebook 02

**What enters:** raw data + the issue list.
**What happens:** **fix before delete.**
* Our row's blank Region: is it recoverable? Yes. Every state belongs to exactly one sales region, and **Texas → Central**. We verified that rule against the data before using it. The row is **kept** and Region becomes `Central`.
* A row with no Sales amount can't be repaired (there's no price list to rebuild it from), so it is removed and logged. Inventing a number would corrupt every total.

**Our row after cleaning:** `... Houston, Texas, Central, OFF-AP-1005, ... 207.30, 10, 0.4, -39.18`
**Notice what was *not* changed:** Profit is **−39.18**, a loss. Negative profit is not an error; it is a real loss, and it turns out to be the most important signal in the project.
**What comes out:** 11,461 trustworthy rows (99.1% kept), 275 repaired values, and a log of every step (`cleaning_log.csv`).
**Why it exists:** if our row had been deleted, or left without a region, Central's 2024 numbers would be wrong, and Central is exactly the region the analysis ends up questioning.
**How we know it's right:** `tests/test_pipeline.py` compares the cleaned data with the error-free original and confirms every repaired value, including this row's region.
**How the next stage uses it:** feature engineering only works on clean, correctly typed data.

## 5 · Feature engineering → `src/feature_engineering.py`

**What enters:** clean rows.
**What happens:** we calculate new, useful columns. For our row:

| New column | Formula | Our row |
|---|---|---|
| Year / Month / Quarter | from Order Date | 2024 / Mar / Q1 |
| Gross Sales | Sales ÷ (1 − Discount) = 207.30 ÷ 0.6 | **345.50** (the price before discount) |
| Discount Amount | Gross Sales − Sales | **138.20** given away |
| Profit Margin % | Profit ÷ Sales | **−18.9%** |
| Discount Band | grouping | 21–40% |
| Is Loss | Profit < 0 | True |
| Shipping Days | Ship Date − Order Date | 5 |

**What comes out:** `data/processed/sales_cleaned.csv` (32 columns).
**Why it exists:** questions like "how much do we give away in discounts?" or "how did 2024 compare with 2023?" become one-line calculations instead of repeated date and price arithmetic.
**How the next stage uses it:** EDA groups and compares using these columns.

## 6 · Exploratory data analysis (EDA) → `notebooks/03_eda.ipynb`, `visualizations/`

**What enters:** the clean, enriched data.
**What happens:** we summarise and chart the data from many angles: by region, over time, by product, by customer, by discount level.
**Patterns found (our row is part of several):**
* Central keeps only **3.3¢ of every $1** sold, against 13.2¢ in the East.
* Every discount level of **30% or more** loses money in total. Our 40%-discount row is one of 1,844 such lines.
* 2024 sales grew while profit fell.

**What comes out:** 13 charts and a list of observed facts.
**Why it exists:** you can't ask good questions before you've seen the data's shape. EDA produces the hypotheses.
**How the next stage uses it:** the patterns become specific business questions.

## 7 · Business questions → `notebooks/04_business_analysis.ipynb`

**What enters:** EDA patterns.
**What happens:** each pattern becomes a precise question with a precise answer, for example *"Is Central's low margin caused by what it sells, or by how it discounts?"* We test it. Central discounts more in **15 of 17** product groups, and on normally discounted lines its margin (17.4%) is about the same as other regions (18.0%). The evidence points to discounting rather than product mix. We also define the **KPIs** precisely, e.g. margin = total profit ÷ total sales, never an average of row margins.
**What comes out:** 17 answered questions and KPI definitions.
**Why it exists:** managers need answers, not charts. And precise definitions stop two people from calculating "margin" two different ways.
**How the next stage uses it:** the same questions are re-asked in SQL, and the KPIs become DAX measures.

## 8 · SQL analysis → `sql/*.sql` (MySQL 8)

**What enters:** the clean data, loaded into a MySQL database.
**What happens:** the key questions are asked again in SQL: totals, regional margins, YoY growth, loss-making products. For example, `business_queries.sql` BQ6 shows Central's effective discount of 21.51%.
**What comes out:** the same numbers, computed by a different engine. They match Python **to the cent** ($4,391,176.00 sales, 5,190 orders).
**Why it exists:** (1) in real companies, data lives in databases and analysts query it with SQL; (2) two independent tools agreeing is strong evidence that the numbers are right.
**How the next stage uses it:** the database uses the same star-schema design that Power BI will use.

## 9 · Star schema → `src/build_star_schema.py`, `data/processed/powerbi/`

**What enters:** the clean table.
**What happens:** the one wide table is split into a **fact table** of numbers plus **dimension tables** of descriptions. Our row becomes:

```
FactSales:    SalesKey 3091 | Order ID US-2024-100748 | Order Date 2024-03-26 | Customer ID RB-10481
              Product ID OFF-AP-1005 | GeoKey 7 | Sales 207.30 | Quantity 10 | Discount 0.4 | Profit -39.18
DimGeography: GeoKey 7 → United States, Central, Texas, Houston
DimProduct:   OFF-AP-1005 → Heavy-Duty Shredder G863, Office Supplies, Appliances
DimCustomer:  RB-10481 → Ravi Brown D., Corporate
DimDate:      2024-03-26 → 2024, Q1, Mar
```

**What comes out:** five CSV files with keys connecting them.
**Why it exists:** each description is stored once; filters flow cleanly from "Central" → GeoKey 7 (and the other Central keys) → the matching sales; and "same period last year" needs a proper calendar table.
**How the next stage uses it:** DAX formulas run on top of these connected tables.

## 10 · DAX → `powerbi/DAX_Measures.md`

**What enters:** the star schema loaded into Power BI.
**What happens:** we write **measures**, formulas that recalculate for whatever is selected. For example:

```dax
Profit Margin % = DIVIDE ( [Total Profit], [Total Sales] )
```

When a manager selects Region = Central and Year = 2024, Power BI keeps only the matching sales (our row among them) and calculates **−0.37%**. Our row's −$39.18 is part of Central's 2024 total profit of −$744.27.
**What comes out:** 31 measures, each with an expected value ([DAX_VALIDATION_CHECKLIST.md](../powerbi/DAX_VALIDATION_CHECKLIST.md)).
**Why it exists:** Python can only answer the combinations we thought of in advance. DAX answers *any* combination, at the moment of the click.
**How the next stage uses it:** every number on the dashboard is one of these measures.
*(Power BI Desktop validation required: this DAX has not been run yet; see PROJECT_CHECKLIST.md.)*

## 11 · Power BI dashboard → `powerbi/Dashboard_Design.md`

**What enters:** the model and the measures.
**What happens:** five pages, one for each audience question: Executive, Regional, Product, Customer, Profitability & Discount. A regional manager clicks "Central" and sees the low margin, the high discount, and the loss-making products. That includes the 40%-discount sales like our shredder.
**What comes out:** an interactive report non-technical people can use without us.
**Why it exists:** insights that live only in a notebook don't change decisions. Managers need to explore the answer themselves.
**How the next stage uses it:** stakeholders confirm the findings by clicking through, which builds trust in the insights.

## 12 · Insights → `reports/Business_Insights.md`

**What enters:** the answers from notebook 04, confirmed in SQL and visible on the dashboard.
**What happens:** each insight is written in four separate parts:
* **Fact:** Central's margin is 3.3%; its effective discount is 21.5% vs ~13.5% in East and West.
* **Possible explanation:** Central's sales teams may have more pricing freedom, or be paid on revenue. *Not proven by the data.*
* **What to investigate:** the discount approval rules and incentive plans.
* **Action:** see below.

**Why it exists:** keeping facts separate from guesses is what makes an analysis trustworthy. Correlation is never presented as cause.
**How the next stage uses it:** recommendations are built only on the facts.

## 13 · Recommendations → `reports/Executive_Summary.md`

**What enters:** insights.
**What happens:** each one becomes an action with an **owner** and a **KPI to check it worked**:
* *Require manager approval for discounts of 30% or more, piloting in Central first.* Our shredder sale (40% off, −$39.18) is exactly the kind of sale this would catch. Selling it at 20% instead would have earned 345.50 × (0.40 − 0.20) = **$69.10** more, *if* the customer still bought it. That "if" is why we recommend a pilot, not a company-wide rule.
* Re-price Tables and Bookcases; add margin to sales targets; investigate South's falling volume.

**What comes out:** a one-page summary for leadership.
**Why it exists:** the whole point of analysis is a better decision.

## The chain in one paragraph

The sales system recorded a messy file. We **understood** it before touching it, **listed** what was wrong, and **cleaned** it carefully. A blank region in Houston became "Central" because Texas is always Central, and we checked that rule first. We **added** helpful columns like gross sales and margin, **explored** the data until patterns appeared, and turned those patterns into **precise answers**. We **re-checked** every important number in a SQL database, **organised** the data into a star schema, and wrote **DAX** formulas so a **Power BI** dashboard can answer any question a manager clicks. Finally, we separated **facts** from **guesses**, and turned the facts into **actions** with owners and ways to measure success. Our single shredder sale, sold at 40% off at a loss in a region that discounts too much, is a small example of the whole story.
