# Data Dictionary

**Dataset:** RetailCo order lines, 1 Jan 2021 – 31 Dec 2024
**Grain (what one row means):** one **product on one order** (an *order line*). One order can contain 1–5 lines.
**Files:** raw = `data/raw/sales_raw.csv` (11,567 rows, with errors) → clean = `data/processed/sales_cleaned.csv` (11,461 rows, 32 columns)

> **About the data.** This is a **synthetic** dataset, generated by `src/generate_data.py` with a fixed random seed. It uses the same column layout as the well-known *Superstore* sample dataset, so the code also works on that file. The business patterns come from rules written openly in the generator (regional growth rates, discount policies, product margins, seasonality). A small, known set of data-quality errors is injected deliberately so the cleaning step has realistic work to do. See [Why synthetic data?](#why-synthetic-data) below.

## Legend

* **Type**: the type *after* cleaning.
* **Missing allowed?**: whether a blank value is acceptable in the clean data.
* **Duplicates?**: whether the same value may appear on many rows (it usually can, so this column says whether that is *expected*).
* **Aggregate?**: whether it makes sense to SUM/AVG it. ❌ means "group or filter by it, don't add it up".

## 1. Original columns (19)

| Column | Type | Business meaning | Expected range / values | Missing allowed? | Duplicates? | Aggregate? |
|---|---|---|---|---|---|---|

| `Order Date` | date | Day the order was placed | 2021-01-01 … 2024-12-31 | No (row removed if invalid) | Yes | ❌ (group by year/month) |
| `Ship Date` | date | Day the order was shipped | ≥ Order Date, ≤ Order Date + 7 days | **Yes**: blanked when it was before the order date | Yes | ❌ |
| `Ship Mode` | category | Delivery service chosen | Same Day, First Class, Second Class, Standard Class | No | Yes | ❌ |
| `Customer ID` | text | Unique customer identifier | `AB-10000` … (741 customers) | No | Yes (repeat buyers) | Count distinct |
| `Customer Name` | text | Customer's name (fictional) | 741 unique names | No (rebuilt from Customer ID) | Yes | ❌ |
| `Segment` | category | Type of customer | Consumer, Corporate, Home Office | No | Yes | ❌ |
| `Country` | category | Country of delivery | United States | No | Yes | ❌ |
| `City` | category | City of delivery | 36 cities | No | Yes | ❌ |
| `State` | category | State of delivery | 28 states | No | Yes | ❌ |
| `Region` | category | RetailCo sales region | Central, East, South, West | No (rebuilt from State) | Yes | ❌ |
| `Product ID` | text | Unique product identifier | `CAT-SC-NNNN` (174 products) | No | Yes | Count distinct |

## 2. Engineered columns (13), added by `src/feature_engineering.py` and `src/data_cleaning.py`

| Column | Formula | Type | Purpose | Aggregate? |
|---|---|---|---|---|
| `Year` | year of Order Date | int | Yearly trends, YoY | ❌ group |
| `Quarter` | `"Q"` + quarter number | text | Quarterly view | ❌ group |
| `Month Number` | 1–12 | int | Correct month sorting, seasonality | ❌ group |
| `Month` | `Jan` … `Dec` | text | Readable labels | ❌ group |
| `Year-Month` | `YYYY-MM` | text | Monthly trend (sorts correctly as text) | ❌ group |
| `Shipping Days` | Ship Date − Order Date | int (nullable) | Delivery speed | AVG ✅ |
| `Profit Margin %` | Profit / Sales × 100 | decimal | Row-level filter (e.g. "lines below 0%") | ❌ **never average**: use SUM(Profit)/SUM(Sales) |
| `Unit Price` | Sales / Quantity | decimal | Price actually paid per unit | ❌ (weighted only) |
| `Gross Sales` | Sales / (1 − Discount) | decimal | Revenue at full list price | ✅ SUM |
| `Discount Amount` | Gross Sales − Sales | decimal | Revenue given away by discount | ✅ SUM |
| `Is Loss` | Profit < 0 | boolean | Count/filter loss-making lines | Count |
| `Discount Band` | No discount / 1-20% / 21-40% / Over 40% | text | Readable discount groups | ❌ group |
| `Is High Value` | Sales > Q3 + 1.5 × IQR (≈ $1,170) | boolean | Flags statistically large lines; **kept** in the data | Count |

## 3. Primary key

The clean table has **no single-column key**. The combination **`Order ID` + `Product ID`** is unique (verified in notebook 02, step 11). In the star schema a surrogate key `SalesKey` (1…n) is added for convenience.

## 5. Business rules used for validation

| Rule | Why |
|---|---|
| Sales > 0 | A sale with zero or negative revenue is not a sale (returns are tracked elsewhere) |
| Quantity ≥ 1 | You cannot sell zero items |
| 0 ≤ Discount ≤ 0.8, from the allowed list | RetailCo's pricing system only allows these levels |
| Region ∈ {Central, East, South, West} and consistent with State | Each state belongs to exactly one region |
| Category consistent with Sub-Category | Each sub-category belongs to exactly one category |
| Ship Date ≥ Order Date | Cannot ship before ordering |
| Profit may be negative | Loss-making sales are real and important |

## Why synthetic data?

| Option | Pros | Cons |
|---|---|---|
| Public *Superstore* file | Real-looking, well known | Unclear redistribution licence; used in thousands of portfolios; already clean, so no real cleaning work |
| **Documented synthetic data (chosen)** | Freely shareable; realistic errors to clean; **ground truth exists**, so cleaning can be *tested* (`tests/test_pipeline.py`) | Patterns come from the generator's rules, so findings show the *method*, not facts about a real company |

**Be honest about this in interviews:** "The data is synthetic, generated with documented business rules so I could share it and test my cleaning against a known truth. The pipeline uses the Superstore column layout, so it runs on real data with no code changes."
